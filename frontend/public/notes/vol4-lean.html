A proof is a program

Lean is a dependently-typed programming language in which propositions are types and proofs are terms. Everything you type — tactics, automation, elaboration — is untrusted machinery whose only job is to construct a term that a small, boring kernel will then re-check from scratch.

§ 0The one-sentence version

Lean's kernel does exactly one thing — decide whether a given term has a given type — and every other part of the system exists to produce terms for it to check. If you understand type-checking and definitional equality, you understand Lean; the rest is ergonomics.

That architecture is called the de Bruijn criterion: a proof assistant should have a small, independently checkable core. Lean's elaborator is roughly 100 000 lines of subtle, heuristic, occasionally buggy code. Its kernel is a few thousand lines and is what you are actually trusting. A bug in the elaborator produces a term that fails to check; a bug in the kernel is a crisis.

What does "a proof is a program" actually mean? Take the statement "if A then B". A proof of it is a method for converting any proof of A into a proof of B — which is to say, a function from proofs-of-A to proofs-of-B.

So if we write A for the type "proofs of A", then "A implies B" is the function type A → B, and a proof of it is literally a function. Modus ponens — from A and A → B, conclude B — becomes function application. This is not an analogy; the two are the same mathematical object, a coincidence discovered independently several times and known as the Curry–Howard correspondence.

The whole design of Lean follows from taking that identification completely seriously: if proofs are programs, then a proof checker is a type checker, and you already know how to write one of those.

§ 1Curry–Howard, by writing programs

Start with what a proof of "if A then B" has to be

Forget types for a moment. Suppose I claim to have proved "if A then B". What have I actually got?

I have a method: hand me any proof of A, and I will hand you back a proof of B. That is what the claim means. If I cannot do that, I have not proved it.

Now notice the shape of that sentence. "Give me an X, I give you back a Y" is the definition of a function from X to Y.

A recipe for pastry is not pastry. It is a procedure that turns flour and butter into pastry. A proof of "A implies B" is likewise not a proof of B — it is a procedure that turns any proof of A into one.
So write it down

Write A for "the collection of proofs of A". Then:

  • "A implies B" is the function type A → B, and a proof of it is literally a function.
  • Modus ponens — from A and A→B conclude B — is function application: you have a : A and f : A → B, so you write f a.
  • "A and B" is a pair: to have both, you must have one of each.
  • "A or B" is a tagged union: you have one of them, plus a tag saying which.
  • False is the empty type: a type with no elements at all, because there is no proof of a falsehood.

Every line of that list was forced. Nothing was chosen for elegance.

Why this is a discovery rather than a notation

It would be unremarkable if someone had merely decided to write logic this way. What happened is stranger: logicians and computer scientists developed these two subjects separately, for unrelated reasons, and the structures turned out to be the same objects. Curry noticed part of it in the 1930s, Howard wrote it up in 1969, and it has since been found again in category theory and in topology.

Two consequences follow immediately, and Lean is built on both. A proof checker is a type checker — and we already know how to write those. And ex falso quodlibet is not an axiom: it is what you get by asking "how do I write a function out of the empty type?", to which the answer is "there are no cases to handle, so you are already done".

§ 2The kernel, and what you are trusting

When you write a Lean proof, this is what happens to it. Click any stage.

2.1The three axioms

Lean's kernel implements the Calculus of Inductive Constructions. On top of it, Mathlib uses exactly three axioms, and #print axioms myTheorem tells you which ones a result depends on:

axiom propext : ∀ {a b : Prop}, (a ↔ b) → a = b
axiom Classical.choice : {α : Sort u} → Nonempty α → α
axiom Quot.sound : ∀ {α} {r : α → α → Prop} (a b : α), r a b → Quot.mk r a = Quot.mk r b

Classical.choice gives excluded middle (via Diaconescu's theorem), propext gives propositional extensionality, and Quot.sound makes quotient types work. A proof printing 'theorem' depends on axioms: [] is fully constructive; one listing Classical.choice is classical. The system makes your logical commitments machine-checkable, which is a genuinely new thing in mathematics.

What is actually being trusted
  • The kernel's correctness. A few thousand lines of C++. Independent re-implementations exist (lean4checker, Trepplein, and others) and can re-verify an entire compiled environment.
  • The axioms' consistency. Carneiro showed Lean's type theory is consistent relative to ZFC plus countably many inaccessible cardinals.
  • That the statement says what you think. The unglamorous failure mode, and by far the most common one in practice. A vacuously-true hypothesis or a subtly-wrong definition is checked just as happily as a correct one.
  • Escape hatches. sorry leaves a hole (Lean warns loudly). native_decide trusts the compiler and its runtime, considerably widening the trusted base — which is why Mathlib does not permit it.

§ 3Type checking is computation

The kernel's central question is not "are these two terms equal?" but "are they definitionally equal?" — do they reduce to the same normal form? Definitional equality is decided by running five reduction rules:

The reduction rules
  • β — apply a lambda: (fun x => e) a ⟶ e[x := a]
  • δ — unfold a definition: Nat.add ⟶ fun m n => …
  • ι — a recursor meets a constructor: Nat.rec z s (Nat.succ n) ⟶ s n (Nat.rec z s n)
  • ζ — expand a let: let x := a; e ⟶ e[x := a]
  • η — functions with the same behaviour are equal: fun x => f x ⟶ f

The consequence is startling the first time: example : 2 + 2 = 4 := rfl works, and it works by computing, not by searching for a proof. rfl : a = a is accepted for a goal a = b precisely when the kernel can reduce a and b to the same term. Drive the machine yourself.

Two different things called "equal"

Ordinary mathematics has one notion of equality. Lean has two, and confusing them is the source of most early frustration.

Propositional equality is the statement a = b. It is a proposition, so it is a type, so proving it means producing a term. That is the normal kind: you prove it with an argument.

Definitional equality is different. Two terms are definitionally equal if they compute to the same thing. This is not proved — it is checked, by running both sides until neither can be reduced further and comparing the results.

Compare 2 + 2 and 4 in a calculator. You do not argue that they are equal; you evaluate and observe. Now compare x + y and y + x: evaluation gets you nowhere, because there is nothing to evaluate until you know what x and y are. That is exactly the line between the two notions.
Which is why rfl can prove arithmetic

rfl is the proof that a thing equals itself — that is its only content. It is accepted for a goal a = b exactly when the kernel can reduce both sides to the same normal form. So example : 2 + 2 = 4 := rfl compiles, and the "proof" is the single word rfl. The work was done by computing, not by searching.

This gives you proof by evaluation. The decide tactic takes a decidable proposition, computes a boolean, and if it is true the whole proof is a rfl. You can prove "there are 25 primes below 100" by running a program, and the kernel confirms it by running the same program.

The asymmetry that trips up everyone

n + 0 = n is provable by rfl. 0 + n = n is not. Both are true. Why the difference?

Because of how Nat.add was defined: it recurses on its second argument. In n + 0, the second argument is the literal constructor zero, so the ι-rule fires immediately and the whole thing collapses to n. In 0 + n, the second argument is a free variable — nothing is known about it, no rule can fire, and the term is stuck.

So this is a fact about the definition, not about arithmetic. Had Nat.add recursed on its first argument, the asymmetry would point the other way. Both statements are true; only one is true by computation — and that is the first moment most people feel that dependent types are genuinely a different animal.

Why is this a big deal? In ordinary mathematics, "2 + 2 = 4" is a theorem you prove. In Lean, it is a computation the checker performs, and the proof term is the single word rfl — "it's the same thing".

That gives you proof by evaluation. decide works this way: it takes a decidable proposition, computes the boolean, and if the answer is true the whole proof is a rfl. You can prove "there are 25 primes below 100" by running a program, and the kernel verifies it by running the program itself.

It also explains a common frustration. Two things that are provably equal need not be definitionally equal. n + 0 reduces to n (the recursion is on the second argument, so it fires immediately), but 0 + n does not — it is stuck on a variable. So rfl proves n + 0 = n and fails on 0 + n = n, which needs an induction. The asymmetry is an artefact of how Nat.add was defined, and it is every beginner's first real surprise.

§ 4Inductive types and their recursors

Almost everything in Lean is an inductive type. You declare constructors; Lean derives the elimination principle automatically, by a fixed schema. Understanding that schema is understanding the foundations.

The schema

Given inductive I with constructors \(c_1,\dots,c_n\), Lean generates I.rec taking:

  • a motive — what you want to produce for each element of I;
  • one minor premise per constructor — how to build the result in that case, given the results for the recursive arguments (the induction hypotheses);
  • a major premise — the actual element you are eliminating.

plus one ι-reduction rule per constructor, saying what happens when the recursor meets that constructor.

Three words, then the idea

The schema above uses three terms that sound like more than they are.

Motive — what you want to produce, for each element of the type. If you are computing a number, the motive is "a number". If you are proving a statement about every \(n\), the motive is "a proof of that statement for \(n\)".

Minor premise — one per constructor, saying how to handle that case. For Nat there are two: what to do for zero, and what to do for succ n given that you already have the answer for \(n\).

Major premise — the actual element you are taking apart.

It is a switch statement with a recursive call built in. "Given a number: if it is zero, do this; if it is one-more-than-\(m\), do that, and you may use the answer for \(m\)." Any programmer has written this a hundred times.
The observation worth stopping for

Write that out for Nat and compare it, line by line, with the principle of mathematical induction: prove it for zero; prove that \(n\) implies \(n+1\); conclude it for all \(n\).

They are not similar. They are the same term. Nat.rec is recursion when the motive lands in Type, and is induction when the motive lands in Prop. Curry–Howard again, at the level of the elimination rule rather than the introduction rule.

This is why Vol. III §1.2 kept insisting on "the smallest set closed under these rules". That phrase is precisely what makes the recursor exist.

Ex falso, for free

Now apply the schema to False, which is declared with no constructors at all. One minor premise per constructor means zero minor premises. So False.rec takes a motive and a major premise and produces… anything you asked for.

Read what just happened. "From a contradiction, anything follows" was not postulated. It is what the general schema degenerates to when the list of cases is empty. You do not have to handle any cases, because there are none. The same schema, applied to Nat, gives you induction. One rule, two of the most-used principles in mathematics.

Pick a type and watch the recursor be derived.

4.1Why recursion has to terminate

Every definition must be seen to terminate, or the logic dies: a non-terminating f : False would prove everything. Lean accepts three routes — structural recursion (compiled to rec), well-founded recursion (compiled to Acc.rec with a decreasing measure), and partial functions marked partial, which are excluded from the logic and usable only for programming.

The strict-positivity condition on inductive declarations is the other half of this. Lean rejects

inductive Bad where
  | mk : (Bad → Bad) → Bad   -- ✗ Bad occurs to the left of an arrow

because such a type would let you embed the untyped lambda calculus, recover fun x => x x, and build a non-terminating term of type False. The occurs-check failure you saw in Fig. 1 and this rejection are the same guard, at two different levels.

§ 5Universes, and why Prop is special

There is no type of all types — Type : Type makes the system inconsistent (Girard's paradox, a typed version of Russell). So Lean has a hierarchy:

\[ \mathtt{Prop} = \mathtt{Sort}\,0, \qquad \mathtt{Type}\ u = \mathtt{Sort}\,(u+1), \qquad \mathtt{Sort}\,u : \mathtt{Sort}\,(u+1). \]

The problem being solved

It would be convenient if there were a type containing all types, so that Type : Type. There is not, and the reason is Russell's paradox wearing type-theoretic clothes.

Russell: consider the set of all sets that do not contain themselves. Does it contain itself? Either answer contradicts the other. Girard showed the same diagonal argument goes through in a type theory with Type : Type, producing a term of type False — which would make every statement provable and end mathematics.

The fix is a tower. Type 0 : Type 1 : Type 2 : …, forever. Every type lives one floor below the thing that contains it, so nothing ever contains itself, and the diagonal has no floor to stand on.

A library catalogue can list every book, but it cannot be one of the books it lists — so you put it on a different shelf. Then a catalogue of catalogues goes on a third shelf. The tower is that, made a rule.
The one place the rule is deliberately broken — safely

At the very bottom sits Prop, and it gets a special dispensation. A proposition may quantify over all propositions, including itself, and remain a proposition: ∀ p : Prop, p → p is itself a Prop. That is impredicativity, and one floor up it would be fatal.

Why is it safe here? Because Prop also has proof irrelevance: any two proofs of the same proposition are definitionally equal. That flattens Prop completely. An element of p : Prop carries exactly one bit of information — whether it exists at all. Girard's diagonalisation needs to distinguish elements of a type in order to build its contradiction, and here there is nothing to distinguish.

What the split pays for, and what it costs

Pays: proofs carry no computational content, so the compiler deletes them entirely — a verified program runs at the speed of an unverified one. And classical axioms like excluded middle are safe in Prop precisely because they destroy no computation; there was none to destroy.

Costs: you cannot generally get data back out of a proof. From ∃ x, P x you may not extract the witness to compute with, because that would leak the information proof irrelevance just erased. This is why Mathlib carefully distinguishes ∃ from Σ, and why Classical.choice has to be an axiom rather than a theorem.

The formation rule for function types is where it gets interesting:

Why the Prop / Type split earns its keep
  • Erasure. Proofs carry no computational content, so the compiler deletes them. A verified program runs at the speed of the unverified one.
  • Proof irrelevance. h₁ = h₂ definitionally for any two proofs of the same Prop. This makes dependent types involving proofs far more usable.
  • Safety of classical axioms. Excluded middle in Prop destroys no computation, because there was none to destroy. In Type it would.
  • The price: restricted elimination. You cannot generally eliminate a Prop into Type — you cannot extract a witness from ∃ x, P x to compute with. (Singleton elimination is the carefully-carved exception that lets Eq and And work.) This is why Mathlib distinguishes ∃ from Σ, and why Classical.choice has to be an axiom rather than a theorem.

§ 6Tactics: the part you actually type

Writing raw terms is unpleasant past a certain size. Tactic mode gives you a goal state — a metavariable with a local context — and tactics are programs that refine it. When the script finishes, the metavariable has been assigned a term, and that is what the kernel sees.

That last claim is the one everything rests on, and it is easier to believe when you can watch it. Below, the proof term is drawn as a tree. Each tactic you apply grows the tree; then the kernel walks the finished tree from the leaves up, re-deriving every type from the axioms with no memory of which tactic put which node there.

§ 7Lean meets Gödel

Lean's kernel is a computably checkable proof system that interprets arithmetic. Volume III therefore applies to it directly and without romance:

  • There is a sentence of arithmetic that Lean can state and cannot prove, assuming Lean is consistent.
  • Lean cannot prove Con(Lean). You can formalise Con(PA) in Lean and prove it, because Lean is stronger than PA — but no system reaches its own consistency.
  • Trusting a Lean proof means trusting the consistency of CIC plus those three axioms, on external grounds. The machine cannot supply that, and it is not a defect of the machine.

What formalisation does deliver is different from certainty and arguably more useful: it collapses the cost of checking. A referee's month becomes a CPU-minute, the exact axioms are printed on request, and every hypothesis is forced into the open. The Liquid Tensor Experiment, the formalisation of the sphere eversion, and the Fermat's Last Theorem project are all bets on that trade.

Formalisation does not give you certainty

It is tempting to think a kernel-checked theorem is certainly true. It is not, and being clear about why is more useful than the slogan.

Three things are still being trusted. The kernel is correct — a few thousand lines of C++, re-implemented independently by lean4checker and Trepplein, which can re-verify an entire compiled environment. The axioms are consistent — Carneiro showed Lean\u2019s type theory is consistent relative to ZFC plus countably many inaccessible cardinals, which is itself an unproved assumption. And by Vol. III, no system can establish its own consistency, so this is not a gap that better engineering closes.

And the statement says what you think it says. This is the unglamorous one, and in practice by far the most common failure.

A spellchecker guarantees every word is a word. It has nothing to say about whether you wrote what you meant. A proof checker guarantees every inference is valid, and has nothing to say about whether the theorem is the one you wanted.
What it does give you, which is different and arguably better

The cost of checking collapses. A referee\u2019s month becomes a CPU-minute. That changes what mathematics is practical, not just what is certain.

Hypotheses cannot hide. A condition quietly assumed in a paper proof has to be written down or the proof does not compile.

Logical commitments become machine-checkable. #print axioms myTheorem tells you whether a result used choice. That was previously a matter of scholarly argument.

So the honest summary is this: formalisation does not make mathematics certain. It makes mathematics auditable, and it makes the audit cheap. Mathlib\u2019s real achievement is less its theorem count than its accumulated, argued-over library of definitions that behave well together — and choosing those is still entirely human work.

The honest failure mode

Formalisation does not protect you from proving the wrong thing. A theorem with a hypothesis that is secretly unsatisfiable is checked with enthusiasm. A definition that does not capture the intended concept yields true theorems about the wrong object. In practice the hard part of formalisation is not the proofs, it is the definitions — and that part is still entirely human. Mathlib's real achievement is less its theorem count than its accumulated, argued-over library of definitions that behave well together.

§ 8Check yourself

A bug is found in Lean's simp tactic that makes it rewrite incorrectly. What is the consequence for existing Mathlib theorems?

This is the entire payoff of the de Bruijn criterion. The trusted computing base is the kernel and the axioms; a tactic is just a term-generator, and a wrong term is rejected. The realistic bad outcome from a simp bug is that proofs stop compiling — annoying, not epistemically alarming. A kernel bug would be the serious case, which is why independent re-checkers like lean4checker exist.

example : n + 0 = n := rfl compiles, but example : 0 + n = n := rfl does not. Why?

Definitional equality is decided by reduction, and reduction on a recursor needs a constructor in head position. In n + 0 the second argument is the literal Nat.zero, so ι fires. In 0 + n the second argument is a free variable and nothing can fire. Both statements are true and provable; only one is true by computation. This asymmetry is a fact about the definition, not about arithmetic — and it is the first thing that makes people say dependent types are weird.

False.rec has no minor premises and produces a term of any type. Where does that come from?

One of the quiet elegances of inductive type theory. You do not postulate "from a contradiction, anything"; you declare a type with no way to build an element, and the automatically-generated eliminator says: to map out of False, supply a case for each constructor — and there are none, so you are already done. The principle drops out of the schema. The same schema, applied to Nat, gives induction.

Why is it safe for Prop to be impredicative when Type : Type is fatal?

Girard's paradox needs to build a type-level structure that distinguishes its own elements and then diagonalise. Proof irrelevance flattens Prop: an element of p : Prop carries exactly one bit — whether it exists — so the diagonalisation has nothing to bite on. This is also why proofs can be erased at compile time, and why Prop's restricted elimination into Type has to be enforced: allowing it would leak the missing information back in.
